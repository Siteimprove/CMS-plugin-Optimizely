# Siteimprove for Optimizely CMS 12 — 4.3.5-beta.1

This private beta lets editors run Prepublish checks on a shared block's draft before submitting it for review or approval. When editing a block, the Siteimprove panel shows only Prepublish. Returning to a page restores its normal page view. Publishing and approval workflows are unchanged.

## Requirements and scope

- Optimizely CMS 12. CMS 13 is outside this package's dependency range.
- Existing Siteimprove Prepublish access and **Latest UI** enabled in the plugin settings.
- A block preview template that renders the selected draft's real HTML and relevant styles. The CMS must provide an editable preview URL on the same origin as the editor. This package does not add preview templates for customer block types.

The beta supports shared blocks, including checks launched from All Properties view. Inline block properties, media, missing preview templates and cross-origin/headless previews without an integration bridge are outside its scope. A fragment scan does not establish that the block is accessible in every containing page's layout. Highlighting needs a matching visible preview.

The package also contains the 4.3.5 settings, URL mapping, overlay loading and automatic recheck fixes. No new settings model or database migration is introduced by the shared-block feature. Existing plugin access roles still apply.

## Before installation

Use a test environment first. Record the installed plugin version and current **Latest UI** setting. Keep the previous application deployment, its package reference/lockfile and its module assets so that it can be redeployed. Back up the CMS database through your normal deployment process. Retain the previous package in a source accessible to your build system.

The delivery contains the package, `SHA256SUMS`, its build manifest and `VALIDATION.md`. Check the package checksum before installation. From the extracted bundle, use either:

```sh
sha256sum --check SHA256SUMS
```

On macOS, use `shasum -a 256 -c SHA256SUMS`. On Windows, compare `Get-FileHash .\SiteImprove.Optimizely.Plugin.4.3.5-beta.1.nupkg -Algorithm SHA256` with the value in `SHA256SUMS`.

## Installation

1. Put `SiteImprove.Optimizely.Plugin.4.3.5-beta.1.nupkg` in a local package folder accessible to the CMS build. For a remote build agent, use an approved private NuGet feed or provide the folder to that agent.
2. Add that folder to the solution's existing `NuGet.config`, preserving its normal package sources. For example, add `<add key="siteimprove-beta" value="./customer-beta" />` inside `<packageSources>` when the folder is next to `NuGet.config`. If the solution uses package source mapping, map the exact package ID `SiteImprove.Optimizely.Plugin` to this source. Do not replace the sources needed for Optimizely and other dependencies.
3. From the CMS project directory, select the exact beta version:

   ```sh
   dotnet add package SiteImprove.Optimizely.Plugin --version 4.3.5-beta.1 --no-restore
   dotnet restore
   dotnet list package
   ```

   If Central Package Management is enabled, update its existing `PackageVersion` entry in `Directory.Packages.props` instead. If locked restore is enforced, regenerate and review the lockfile for this intentional package update, then resume locked restores. Avoid unrelated dependency updates.
4. Build and deploy through the site's usual process, including the package's `modules/_protected/SiteImprove.Optimizely.Plugin/SiteImprove.Optimizely.Plugin.zip` asset. Restart the application and reload the CMS editor to load the new scripts. Confirm the resolved plugin version is `4.3.5-beta.1`.
5. Open the Siteimprove configuration in CMS Admin and enable **Latest UI**. Keep the site's existing credentials, URL mappings and automatic recheck preferences. An administrator must have one of the plugin's allowed roles: Administrators, WebAdmins, CmsAdmins or SiteimproveAdmins.

The package is supplied privately; it does not require publication to the public Optimizely feed. See Microsoft's [package installation guidance](https://learn.microsoft.com/en-us/nuget/consume-packages/install-use-packages-dotnet-cli) for version selection.

## Customer acceptance

1. Open a normal page and confirm the usual Siteimprove page view.
2. Open a shared block with a draft preview. Confirm that only Prepublish is offered, without the previous page's report.
3. Make a draft-only change with a known issue, such as a non-decorative image without a text alternative. Save the draft and run a check before submitting it for approval. Confirm the scan completes and detects the issue.
4. Fix the issue, save, reload the editor to confirm persistence, then run a fresh check. Confirm the issue clears. Leave the draft unpublished during this verification.
5. Return to a page and confirm that its normal tabs and report return. Repeat with a representative customer block type and language.

If the scan action is unavailable, confirm Prepublish access, Latest UI and the block's same-origin editable preview. A failed or inaccessible preview cannot supply a valid scan. Report the CMS version, block type, steps, visible result and any browser/server error to your support contact; omit credentials.

## Rollback

1. Redeploy the previous complete application build, including its plugin DLL and module ZIP. This is the preferred rollback because it restores the exact previous assets and dependencies.
2. If rebuilding instead, restore the previous package reference (or central version), NuGet sources and lockfile from the pre-beta revision. Restore, build and deploy the full application. For a project without central version management, the package command is `dotnet add package SiteImprove.Optimizely.Plugin --version <previous-version> --no-restore`, with the recorded version substituted. Confirm the previous package is available to the build system.
3. Restart the application and reload the editor. Check that the old version is resolved and that the module ZIP comes from that version. Do not leave a beta module ZIP alongside the old DLL.
4. Restore the recorded Latest UI setting if it was changed for the beta. Verify page reports, plugin configuration and a draft save. Independent block checks will no longer be available on versions that do not support them.

The shared-block feature does not require database restoration for rollback. A full database restore would also revert unrelated editorial work; use your normal recovery procedure only if a separate deployment problem requires it.

Disabling Latest UI stops this beta's block scan support, but it also changes the Siteimprove interface and does not revert the installed package. Use the package rollback above to fully revert the beta.
