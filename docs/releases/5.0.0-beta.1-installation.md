# CMS 13 beta.1 installation and rollback

Use an isolated, non-production CMS 13 installation with .NET 10 and synthetic content. Review the release notes and attached dependency report first. This package does not upgrade a CMS 12 application or its database to CMS 13.

## Before installation

1. Confirm that the host already runs CMS 13 and its required platform services. The development checks exercised CMS 13.0.0 locally and CMS 13.0.2 on the Windows demo, using local ASP.NET Identity; Opti ID/Graph acceptance remains open.
2. Back up the CMS database, content/blob storage, host configuration, current package references and complete running deployment. Record a restore procedure and the previous plugin version.
3. Download `SiteImprove.Optimizely.Plugin.5.0.0-beta.1.nupkg` and `SHA256SUMS` from the same GitHub prerelease. Verify the checksum with `sha256sum -c SHA256SUMS` or Windows `Get-FileHash -Algorithm SHA256`. The release manifest identifies the source commit and validation run.
4. Keep a public server-rendered page and a shared block with an editable same-origin preview template. The same origin means the same scheme, hostname and port. The plugin does not supply templates for your block types.

## Install from a local package feed

Copy the downloaded `.nupkg` into a dedicated local feed directory. Add that directory as a package source in the host's existing NuGet configuration, preserving its NuGet.org, Optimizely and private sources. For example:

```sh
dotnet nuget add source /absolute/path/to/beta-feed --name siteimprove-beta --configfile /path/to/host/NuGet.config
dotnet add /path/to/host/Host.csproj package SiteImprove.Optimizely.Plugin --version 5.0.0-beta.1
dotnet restore /path/to/host/Host.csproj --configfile /path/to/host/NuGet.config
dotnet publish /path/to/host/Host.csproj -c Release -o /path/to/clean-staging
```

Use a new staging directory and verify that it contains the plugin assembly and `modules/_protected/SiteImprove.Optimizely.Plugin/SiteImprove.Optimizely.Plugin.zip`. Keep host-specific settings, licenses and content in their existing deployment process. Stop or drain the test application, deploy the staged build, restart and verify its homepage and CMS login. Refresh the editor to load the new versioned resources.

## Check the installation

- Open Siteimprove from the CMS editor and sign in with the intended Siteimprove account. Prepublish access follows that account's subscription. Connection setup is automatic; no legacy CMS API credentials or activation step are required.
- Verify existing public-origin mappings in CMS settings. Test saves with an administrator, and plugin access with an ordinary permitted editor. Typical use roles include CmsEditors, WebEditors and SiteimproveEditors; settings require Administrators, WebAdmins, CmsAdmins or SiteimproveAdmins. Validate your actual identity/group mapping.
- Check that a page opens the correct published report. Run a draft check with a ready same-origin preview.
- Open a shared block directly. It should show only Prepublish. From All Properties, scan a known draft issue, correct it, save, reload to verify persistence and recheck without publishing. The corrected finding should disappear. Review the visible-preview scan limitation in the release notes.
- Ensure that your CMS 13 block template renders the actual block. An old Alloy content-area DisplayFor template rendered headings without the block body; CMS 13 property/item tag helpers fixed that demo template. Do not accept an empty-preview scan as evidence that authored content was checked.
- Review the host's Content Security Policy and browser console for blocked CMS/SDK resources. Do not disable CSP or add broad exceptions to make a test pass.

Publishing does not trigger an automatic Siteimprove recheck. Checks are advisory and do not block publication. The [acceptance guide](../cms13-testing.md) contains the broader matrix and expected failure behavior.

## Roll back

Stop the test host and restore the previous package reference and host source/configuration. Remove only the Siteimprove protected-module folder copied into that host project, then restore/build/publish into a new clean directory so the previous package supplies its module. Deploy the previous known-good build and restart. Never remove unrelated CMS modules.

For the most direct recovery, restore the complete pre-install deployment through your normal deployment process. If a test also upgraded CMS or changed the database, restore the matching pre-test database, content and configuration together; removing the plugin does not reverse a CMS database upgrade.

Retain the failing candidate version, sanitized reproduction steps and previous deployment until rollback is verified. Do not attach authentication material or private content to a public issue.
